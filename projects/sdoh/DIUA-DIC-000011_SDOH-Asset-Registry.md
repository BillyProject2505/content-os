## 1. Purpose

This document is SDOH's authoritative identity registry for reusable visual assets — objects that appear repeatedly across content and must stay identifiable and consistent, as distinct from one-off content decisions. It assigns a permanent Canonical Object Identifier (`SDOH-OBJ-<6DigitSequence>`) to each asset.

This document registers identity and core spec together (name, values, usage rule) in one place — a lighter-weight model than CWC's separate Identity/Specification/Visual-Reference split (CAR/CAB/CRS), scoped to SDOH's simpler asset count. If SDOH's assets grow substantially in number or complexity (e.g. a recurring character needing a detailed locked visual spec), splitting into separate documents following CWC's pattern should be reconsidered at that point — not before.

## 2. Scope

**In scope:** reusable visual objects — logo variants, surface/background colors, recurring graphic ornaments, recurring character identity, canonical background textures, reusable supporting marks, and any genuinely cross-format typeface identity — that appear across multiple pieces of content and need one stable definition.

**Out of scope:** one-off content decisions; pose choice for a specific piece; format-specific typography metrics (size, leading, tracking, text width, coordinates); layout mechanics; pacing; motion; sequencing; content pillars/copy (Project Architecture §5); production process (Production SOP).

## 2.1 Canonical Binary Storage & Resolution Authority

**Canonical short form:** `Resolve in Linear → fetch exact binary from Google Drive → compute SHA-256 independently → compare to active checksum → Produce; otherwise FAIL CLOSED.`

This short form is normative for all new SDOH production runs.

**OWNER-LOCKED — 2026-09-20 — GOOGLE DRIVE ONLY.**

SDOH now uses one active persistent-binary provider:

* **Linear / SDOH Asset Registry** = authority for reusable asset identity, semantic scope, canonical SHA-256, provenance state, and active Google Drive locator.
* **Google Drive** = the sole active persistent binary store for SDOH production assets and current canonical implementation packages.
* Dropbox locators/content hashes retained elsewhere in this document or historical issues are **historical provenance only** after this migration. They must not be used to source active production binaries.
* File Library, chat/runtime copies, historical Linear attachments, previews, local caches, and visually similar replacements are not production authority.

### Production Resolution Contract — Google Drive Only

For every reusable asset or implementation binary required by a production job:

1. Resolve the active asset/object/implementation record from Linear.
2. Resolve the exact Google Drive file ID recorded by the active authority.
3. Fetch the exact raw bytes from that Google Drive file.
4. Compute SHA-256 independently over the raw bytes.
5. Compare the computed SHA-256 with the active canonical SHA-256 recorded in Linear.
6. **MATCH → PASS / PRODUCE.**
7. **MISSING / MISMATCH / UNVERIFIABLE → FAIL CLOSED / NON-PRODUCTION.**

No provider fallback is permitted for active production. Do not redraw, regenerate, approximate, reconstruct, recompress, or substitute a visually similar file and call it canonical.

A single byte-identical physical source may intentionally satisfy multiple registered roles/object identities when this registry records that relationship. Duplicate storage is not required merely to mirror object numbering.

This rule governs binary resolution only. Format-specific placement, crop, scale, motion, timing, sequencing, and semantic deployment remain owned by the applicable production lane.
