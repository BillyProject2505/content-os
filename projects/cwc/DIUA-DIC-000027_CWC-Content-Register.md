## 1. Purpose

CWC Content Register is the authoritative operational index for CWC content instances. Its primary purpose is to prevent accidental republication of materially identical content while preserving legitimate topic reuse, intentional repurposing, and controlled reposting.

The register records **what CWC has communicated and published**. It does not replace the Production Bible, Production Workflow, format specifications, asset registries, QA mechanism, or platform analytics.

---

## 2. Core Rule

> The same topic is not automatically duplicate content.

Duplicate assessment is based on the combination of:

`Topic + Learning Objective + Core Message + Editorial Angle`

A new headline, visual treatment, caption, or format does not by itself make substantively identical content new.

## 3. Content Instance Identifier

### 3.1 Canonical grammar

```text
CWC-{FORMAT}-{NNNN}
```

Current approved lanes:

```text
CWC-REEL-NNNN
CWC-CRSL-NNNN
CWC-POSTER-NNNN
CWC-POST-NNNN
CWC-STORY-NNNN
```

### 3.2 Identifier rules

 1. Sequence is independent per format lane.
 2. A sequence number is never reused.
 3. One content instance has one Content ID.
 4. Copy, caption, design, master, or metadata revisions retain the same Content ID.
 5. A cross-format adaptation receives a new Content ID and records `Adapted From` / `Source Content ID`.
 6. A repost does **not** receive a new Content ID; it creates another Publication Log record.
 7. Title changes do not change the Content ID.
 8. Content Pillar, Series, Topic, Campaign, and platform are metadata and are not identifier components.
 9. Reusable assets remain in the `CWC-OBJ-*` namespace and must not be represented as content instances.
10. `DIUA-DIC-*` identifies governed documents, not content instances.
11. The carousel lane token is `CRSL`. The former token `CAR` is **RETIRED** and must not be used for content instances (see §3.2.1).

### 3.2.1 Carousel lane token — OWNER DECISION 2026-09-19

The carousel content-instance lane is `CWC-CRSL-{NNNN}`. It replaces the former `CWC-CAR-{NNNN}` token.

**Basis.** `CWC-CAR` collided with the established abbreviation of the CWC Canonical Asset Registry (`CWC-CAR`, [BUS-20](DIUA-DIC-000014_Coz-We-Care-Canonical-Asset-Registry-CAR.md)), mixing **document identity** with **content-instance identity** — the exact separation rules 9 and 10 above exist to protect. The Owner resolved this on 2026-09-19 by renaming the lane token.

**No identifier was invalidated.** No `CWC-CAR-*` Content ID was ever allocated: at the time of this decision the register held only `CWC-POSTER-0001`–`0003`, and the REEL, carousel, and POST lanes were all still at next = `0001`. The immutability rule (§14.2) and the non-recycling rule (§14.3) are therefore untouched — this is a rename of an unused lane token, not a reassignment of any existing content identity.

**Retired token.** `CWC-CAR-{NNNN}` is retired and must never be allocated. Occurrences of the old token in this document's historical change-log entries are preserved as provenance and are not current grammar.

### 3.2.2 Story lane token — OWNER DECISION 2026-09-23

The Story content-instance lane is `CWC-STORY-{NNNN}`.

**Mapping.** `FORMAT-STORY` content instances use the native `STORY` lane token. This preserves the direct relationship between registered format identity and content-instance identity without overloading `POST`, `REEL`, or another existing lane.

**Activation.** The lane activates prospectively under the existing forward-only cutover model. The first native allocation is `CWC-STORY-0001`. Sequence values represent allocation order, not historical Story publication chronology.

**Scope.** This decision adds one format lane only. It does not alter duplicate-control semantics, lifecycle states, adaptation/repost rules, Publication Log behavior, or identifiers already allocated in other lanes.

### 3.3 Sequence activation state

**RESOLVED BY OWNER-LOCKED FORWARD-ONLY CUTOVER.**

CWC has pre-existing content history that is not fully reconciled into this register. That incomplete history no longer blocks namespace activation because the approved cutover separates legacy evidence from native Content ID allocation.

The Content Register namespace is ACTIVE with v1.0 canonicalization. The first native allocation in each format lane is `0001`. Sequence values represent allocation order only and must never be interpreted as historical publication chronology.

### 3.4 Allocation sequence semantics — OWNER-LOCKED

`NNNN` should represent **Content ID allocation order within a format lane**, not historical publication chronology.

Under this interpretation:

* `CWC-CRSL-0001` means the first carousel Content ID allocated by this register, not necessarily the oldest carousel CWC ever published;
* the same rule applies independently to REEL, POSTER, POST, and STORY;
* historical publication date remains publication metadata and must never be inferred from the numeric sequence;
* incomplete legacy history therefore does not need to block clean namespace activation.

**Owner-locked decision:** `NNNN` represents Content ID allocation order within its format lane. This decision is canonical for [BUS-57](https://linear.app/bussiness-content-os/issue/BUS-57/cwc-content-register) and must not be reinterpreted as publication chronology.

## 5. Semantic Key

The manual semantic signature is:

```text
PILLAR :: TOPIC :: LEARNING-OBJECTIVE :: CORE-MESSAGE :: EDITORIAL-ANGLE
```

The Semantic Key is a search and comparison aid, not a second identifier namespace.

Format is deliberately excluded from the Semantic Key because materially identical content can exist across different formats.

---

## 6. Duplicate Classification

### D0 — No Conflict

Topic may overlap, but the Learning Objective and/or Core Message is materially different.

**Decision:** ALLOW.

### D1 — Related Content

Content is editorially related but delivers a distinct lesson or angle.

**Decision:** ALLOW and record `Related Content` where useful.

### D2 — Semantic Overlap

Topic, Learning Objective, and Core Message are substantially similar, while the proposed angle may still provide meaningful new value.

**Decision:** REVIEW before production.

### D3 — Duplicate

Topic, Learning Objective, Core Message, and Editorial Angle are materially the same as an existing content instance.

**Decision:** BLOCK as a new content instance unless explicitly handled as an approved update, intentional repurpose, or repost.

---

## 7. Intentional Repurposing

Repurposing is allowed when intentional and traceable.

A cross-format adaptation:

* receives a new Content ID in the target format lane;
* records `Adapted From` / `Source Content ID`;
* preserves the relationship to the source content;
* must not be presented as unrelated new editorial work when its lesson is inherited.

Example:

```text
CWC-CRSL-0027
↓ adapted into
CWC-REEL-0014
Adapted From: CWC-CRSL-0027
```

---

## 8. Repost Rule

A repost is a new **publication occurrence**, not a new content instance.

The Content ID remains unchanged. Each posting event is recorded in the Publication Log.

Example:

```text
Content ID: CWC-REEL-0014
Publication occurrence 01: original publication
Publication occurrence 02: approved repost
```

A repost must never be disguised as a new Content ID merely because the publication date, caption, crop, thumbnail, or platform placement changed.

## 9. Workflow Lifecycle Synchronization

The CWC Content Register does **not** define an independent content lifecycle.

Lifecycle authority remains exclusively with the canonical CWC Production Workflow. For any native Content ID, this register stores the current Workflow Lifecycle State as synchronized operational metadata.

Under CWC Production Workflow v1.22 CANONICAL LOCKED, native Content ID allocation occurs during STG‑02 DEFINITION after the semantic duplicate disposition permits progression; STG‑10 additionally requires an Approved Release Identity before `READY_FOR_PUBLICATION`, while `PUBLISHED` requires platform-confirmed live evidence. Therefore the earliest normal workflow state recorded for a newly allocated content instance is the state produced by successful DEFINITION exit (`DEFINED`).

The register may mirror subsequent canonical workflow states, including but not limited to:

```text
DEFINED
RESEARCHED
PLANNED
IN_CONTENT_PRODUCTION
CONTENT_PRODUCED
IN_ASSET_PREPARATION
ASSETS_PREPARED
IN_VISUAL_PRODUCTION
READY_FOR_QA
QA_PASSED
READY_FOR_APPROVAL
APPROVED
READY_FOR_PUBLICATION
PUBLISHED
CANCELLED
```

The exact authoritative state set and transition semantics are owned by the CWC Production Workflow and must not be redefined here. If the Workflow changes its state model, this register follows it through controlled cross-document conformance rather than creating aliases.

`BLOCKED` and `GOVERNANCE_REVIEW` are workflow **Exception Statuses**, not Lifecycle States. They may be mirrored in the optional `Exception Status` field while the underlying Lifecycle State remains frozen according to the Workflow.

A Content ID that reaches `CANCELLED` remains permanently allocated and is never recycled. A `PUBLISHED` item remains in the register even if a platform post is later deleted. Editorial supersession, versioning, or replacement is represented through relationship/version metadata rather than by inventing an additional lifecycle state in this register.

## 10. Pre-Production Duplicate Gate

Before a new CWC content concept proceeds into production:

1. Search the register for the same or adjacent Topic.
2. Compare Learning Objective.
3. Compare Core Message.
4. Compare Editorial Angle.
5. Check `Adapted From` and `Related Content` relationships.
6. Assign D0, D1, D2, or D3.
7. Apply the corresponding decision:
   * D0 → proceed;
   * D1 → proceed with relationship recorded where useful;
   * D2 → editorial review required;
   * D3 → block as new content or convert to an explicitly documented repurpose/repost/update path.

This register defines the duplicate-control decision model. The corresponding workflow integration is authoritative in CWC Production Workflow v1.22 CANONICAL LOCKED at STG‑02 DEFINITION, with publication-readiness identity locking at STG‑10 and closure synchronization at STG‑11 RECORD.

## 13. Historical Migration Rule

Historical migration must preserve uncertainty rather than inventing facts.

For each discoverable legacy CWC content item:

1. identify the artefact or publication evidence;
2. determine its format;
3. reconstruct Topic, Learning Objective, Core Message, and Editorial Angle from the actual content;
4. check whether multiple platform posts represent the same content instance or genuinely different instances;
5. when a legacy item is specifically imported into the native register, assign one Content ID to that imported content instance using the then-next available sequence in its format lane;
6. add every verified publication occurrence to the Publication Log;
7. mark dates, URLs, masters, or provenance as `UNKNOWN` when they cannot be verified;
8. never choose a retroactive sequence to imitate legacy chronology; imported legacy items use the then-next available native sequence under the Owner-locked forward-only cutover.

Migration order must not be represented as publication chronology unless chronology is independently verified.

Sequence activation follows the **Owner-locked forward-only cutover rule** below. Full historical reconciliation is not a prerequisite for activation, provided legacy staging continues to participate in duplicate screening and no retroactive numbering is used to simulate chronology.

### 13.1 Forward-only legacy cutover model — OWNER-LOCKED

For CWC, full historical backfill is not required to satisfy the register's primary duplicate-prevention purpose.

**Locked cutover rule:**

1. All content published before Content Register activation remains **LEGACY / STAGING** unless specifically imported later.
2. Legacy staging rows continue to participate in duplicate screening even without native Content IDs.
3. Native sequences begin cleanly at `0001` per format lane when the register is activated:
   * `CWC-REEL-0001`
   * `CWC-CRSL-0001`
   * `CWC-POSTER-0001`
   * `CWC-POST-0001`
4. Sequence numbers represent allocation order, not publication chronology.
5. If a legacy item later needs an exact repost, controlled update, or stronger provenance, that item may be imported at that time and receive the next available Content ID in its format lane. Its historical publication date remains metadata.
6. Importing one legacy item does not require backfilling every older item.
7. A legacy item must not receive a retroactive number chosen to simulate historical chronology.

This model is **Owner-approved and locked**. It prevents fabricated historical sequencing while allowing the register to become operational without full legacy backfill.

## 14. Governance Constraints

1. The register records application; it does not redefine CWC editorial, visual, format, asset, or QA standards.
2. Content ID is immutable after allocation.
3. Sequence values are never recycled after cancellation, deletion, or supersession.
4. Semantic similarity is judged from actual communication intent, not title matching alone.
5. D3 content cannot be registered as a new instance solely by changing wording, caption, thumbnail, or visual treatment.
6. Intentional adaptation and reposting must remain traceable to the original content instance.
7. Publication evidence and content identity are separate: one content instance may have zero, one, or many known publication occurrences.
8. Unknown history must remain explicitly unknown until verified.
