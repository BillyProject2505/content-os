## 1. Purpose

This document defines the architecture by which a **CWC content format** (Poster, Carousel, Reel, Story, and future formats) **specializes** the canonical CWC Core Production Workflow `[REV1.0]`, so that CWC can support multiple content formats while preserving exactly one Core Production Workflow.

The Core Workflow already reserves this exact role for a future document: it names "Format Specialization" as one of its own architectural sections `[REV1.0 §17]`, states the extension-only principle as a numbered Workflow Principle (`[REV1.0 §4]`, principle 10: "Extension, not forking"), enforces it as a standing invariant (`[REV1.0 §20]` INV‑FMT‑1: "Format Specifications extend Core stages and never redefine Core Lifecycle States or Exception Statuses"), and explicitly states that format specifications are "built as separate artifacts after this document is locked — none authored here" `[REV1.0 §17]`. This document is that separate artifact. It does not amend, reinterpret, or reopen `[REV1.0]`; it operationalizes the extension contract `[REV1.0]` already declared for itself.

## 2. Scope

**In scope:** the Format Specialization Object schema; the Inheritance / Extend / Constrain rule system and the Forbidden-Override validation classification; the Stage Attachment Model (where and how a format may attach requirements to the Core Workflow's already-defined Stage Contracts); the Format Registry model; validation and conformance criteria for a Format Specialization; the Format Addition (registration) gate; versioning and change-control rules across three independent version axes (Core Workflow, this specification, individual formats); the authority/boundary model separating this document from the Core Workflow, from CPB/CAS/CAR/CAB/CRS, and from Content OS's own root-level structural/governance documents; minimal illustrative examples.

**Out of scope:** redesigning or reopening `[REV1.0]`'s own architecture; a Revision 2 of the Core Workflow; full Poster/Carousel/Reel/Story production specifications (only minimal example records are given here); step-by-step production SOPs; AI agent orchestration/tool-calling/event-bus/database/API architecture; Linear/GitHub/Canva implementation detail; redesign of CAS/CAR/CAB/CRS; new governance authority beyond what `[REV1.0]` and the CAS ecosystem already establish; Campaign/Series-level orchestration (an explicitly open Core Workflow question, `[REV1.0 §21 Appendix B, item B‑4]`, not this document's to resolve); resolution of `BUS-35`–`BUS-39` (the Core Workflow's own carried-forward Open Decisions) unless this document's own architecture genuinely requires it — it does not.

## 3. Definitions

* **Content Item** — the single unit that moves through the Core Workflow, holding exactly one Stage, one Lifecycle State, and (optionally) one Exception Status at a time `[REV1.0 §3]`. This document does not redefine it; **Format is an attribute of the Content Item**, assigned once at Planning `[REV1.0 §6 STG‑04]`, never a competing workflow unit. **Current cardinality:** under this model, a Content Item carries **exactly one** assigned Format Specialization at a time (§5) — `[ARCHITECTURAL INFERENCE]` drawn from STG‑04's singular "assigned Format Specialization" wording, not an explicit platform-wide cardinality rule stated by `[REV1.0]` itself. Concurrent assignment of more than one Format Specialization to a single Content Item is not supported by the current FSS-001 architecture; see OD‑3 (§18) for the distinct, future-facing question of whether that capability should ever be introduced by explicit amendment.
* **Format** — a recognized, registered category of Communication Artefact production (e.g. Poster, Carousel, Reel, Story) governing what additional requirements, constraints, and validation criteria apply to a Content Item beyond the Core Workflow's own Stage Contracts.
* **Format Specialization** — the bounded act of attaching format-specific requirements to specific, already-existing points of the Core Workflow's Stage Contracts `[REV1.0 §6]`, without altering the Stage sequence, Lifecycle State values, Exception Status values, transition logic, or governance model. See the operational definition at `[FSS-001 §6, Q1]`.
* **Core Stage Contract** — the Input/Output Contract model already defined per stage by `[REV1.0 §6]` (Purpose, Required Inputs, Input Preconditions, Core Activities, Output Package, Output Contract, Output Validation, Exit Criteria, Failure Conditions).
* **Stage Attachment Point** — one of the eleven Core Stages, considered as a location where a Format Specialization may (but need not) attach additional requirements.
* **INHERIT / EXTEND / CONSTRAIN** — the three declarable rule modes governing what a Format Specialization may state at any given Stage Attachment Point. **FORBIDDEN OVERRIDE** is not a fourth declarable mode; it is the validation classification (§9, §12) applied to a clause that, on inspection, actually replaces, weakens, skips, or redefines Core Workflow architecture. Defined in full at `[FSS-001 §9]`.
* **Format Specialization Object** — the canonical schema (§8) in which one format's specialization content is recorded.
* **Format Registry** — the minimal index of recognized, registered formats (§11), consulted by the Core Workflow at `[REV1.0 §6 STG‑04]`'s Output Contract clause "format recognized."

## 6. Format Specialization Model

### Q1 — What is a Format Specialization? (operational definition)

> A Format Specialization is a named, registered, version-controlled set of additional Inputs, Core-Activity extensions, Output-Package elements, Output-Contract constraints, Production Requirements, Asset-Requirement categories, and Validation-Requirement contributions, each attached to one or more of the Core Workflow's eleven Stage Attachment Points, governing exactly one recognized Format, and bound by the rule system of `[FSS-001 §9]`. It attaches; it never forks.

**Cardinality (current model):** "governing exactly one recognized Format" above is architectural, not incidental — a Content Item's assigned Format Specialization is exactly one Format Specialization Object at a time (§3, §5). A Content Item's `stage_attachments` set belongs to that single assigned Format Specialization Object; it is never a merged or runtime-composed set drawn from more than one Format Specialization Object. See OD‑3 (§18) for the distinct question of whether a future capability for concurrent multi-format assignment should ever be introduced.

### Q2 — What does a format inherit from the Core Workflow?

Every Format Specialization inherits, unconditionally and without restatement:

* the eleven-stage sequence and its order `[REV1.0 §5]`;
* the Content Item as the sole workflow unit `[REV1.0 §3]`;
* the three-dimension data model (Stage / Lifecycle State / Exception Status) `[REV1.0 §5]`;
* the Stage–Lifecycle State Validity Matrix `[REV1.0 §8.2]`;
* the Exception Status model and its transition table `[REV1.0 §9]`;
* the Revision Event model and defect-routing table `[REV1.0 §11]`;
* the three Quality Gates and the general transition-condition mechanism `[REV1.0 §12]`;
* the Publication and Cancellation boundaries, both atomic, both one-way `[REV1.0 §15]`;
* the four Human Approval Points `[REV1.0 §18]`;
* the Asset Lifecycle boundary — a format *references* the CAS Canonical Lifecycle, it never restates or owns it `[REV1.0 §16]`;
* RECORD as the sole terminal Stage `[REV1.0 §19]`;
* tool independence `[REV1.0 §20 INV‑TOOL‑1]`.

None of the above is restated inside a Format Specialization Object; the schema (§8) has no fields for any of them, by design — restating an inherited rule inside a format record would itself be a conformance defect (§12, Conflict Detection).

### Q3 — What may a format override?

**Nothing, in the literal sense of "override."** `[REV1.0]`'s own rule 3/4 (§5 above) and INV‑FMT‑1 categorically forbid redefining a Stage, a Lifecycle State value, an Exception Status value, a Quality Gate, or the governance/approval model. This document does not weaken that: **FORBIDDEN OVERRIDE is not a fourth mode a format may select — it is the whole class of validation failure** the rule system (§9) exists to detect, defined broadly rather than as a per-field enumeration, precisely so a future format cannot find an ungoverned gap.

The one override-adjacent mechanism a format *is* permitted is **CONSTRAIN** (§9) — narrowing an already-generic Core requirement (e.g. a generic Exit Criterion) into a more specific, still-compliant form, never a contradiction of it. Format-specific creative or structural flexibility is achieved through **EXTEND** (adding new, format-owned requirements the Core Workflow is silent on), not through weakening anything the Core Workflow already states.

### Q4 — What may a format add?

Nine bounded classes of addition, each mapped to a specific field in the schema (§8) and a specific Stage Attachment Point (§10):

1. Format-specific **Inputs** — additional Required Inputs consumed alongside a Stage's existing Core inputs (e.g. `[REV1.0 §6 STG‑05]` already names "Format Specialization content requirements" as a Required Input; `[REV1.0 §6 STG‑07]` already names "Format Specialization visual requirements").
2. Format-specific **Core-Activity extensions** — additional activities performed *within* a Stage's existing Core Activities, never a new Stage.
3. Format-specific **Output-Package elements** — additional structure within an existing Output Package (e.g. a Carousel's Content Draft becomes a structured multi-slide draft; it is still one Output Package).
4. Format-specific **Output-Contract constraints** (CONSTRAIN-class only) — narrower Exit Criteria, never a weaker or contradictory one.
5. Format-specific **Production Requirements** — concrete parameters (dimensions, duration, slide count) that a Core Activity must honor. Represented in the schema by the dedicated `production_requirements` field (§8) — never folded into `additional_output_elements` or `additional_output_contract_clauses`, which are distinct classes (items 3 and 4).
6. Format-specific **Asset-Requirement categories** — categories/counts of assets required (e.g. "one primary logo lockup," "one footer-platform placement"), referencing existing CAR/CAB/CRS-owned identifiers only for illustration, never inventing new ones and never asserting a specific identifier as the format's own requirement (§10 STG‑06; Q8 below).
7. Format-specific **Validation-Requirement contributions** — additional criteria supplied into STG‑08's existing "applicable QA criteria" Required Input `[REV1.0 §6 STG‑08]`, never a second QA mechanism (Q7 below).
8. Format-specific **Handoff detail** — additional fields carried inside an existing Output Package/Contract, never a new handoff route beyond `[REV1.0 §7]`'s Stage Handoff Matrix.
9. Format-specific **sub-status metadata** within a Core Lifecycle State, exactly as `[REV1.0 §17]` rule 4 already permits, and no more.

### Q5 — Where does specialization attach to the Core Workflow?

Mapped explicitly in §10 (Stage Attachment Model). Not every Stage requires attachment for every format — most formats need attachment at only 3–4 of the eleven Stages.

### Q6 — How are format-specific requirements represented?

As a set of **Stage Attachment Blocks** inside the Format Specialization Object (§8), one optional block per Core Stage, each block declaring exactly one rule mode (EXTEND or CONSTRAIN, §9) and using the nine addition classes (Q4) consistent with that mode. This is the "normalized representation": uniform across every format, uniform across every Stage, and — because it reuses the Core Workflow's own existing field names (Required Inputs, Core Activities, Output Package, Output Contract, Output Validation) rather than inventing new ones — directly traceable back to `[REV1.0 §6]` without a translation layer.

### Q7 — How does QA consume format-specific requirements?

Without creating a second QA architecture. `[REV1.0 §6 STG‑08]` already lists "applicable QA criteria" as one of QA's Required Inputs, independently of any format. A Format Specialization's Validation-Requirement contributions (Q4, item 7) are simply one additional source feeding that one existing input. QA's Output Contract is unchanged by this: "a verdict is recorded, and a FAIL is never recorded without a classified defect" `[REV1.0 §6 STG‑08, §12.3]`. There is one QA lifecycle, one verdict mechanism, and one Gate‑QA / Gate‑Approval pair `[REV1.0 §12.1]`, regardless of how many formats exist or how many criteria sources feed into "applicable QA criteria." This document does not, and architecturally cannot, resolve *who owns* the underlying QA checklist — that is `[REV1.0 §21 Appendix B, item B‑5]`, explicitly carried forward as open (`BUS-38`) — but Q7's architecture holds regardless of how B‑5 is eventually resolved (§18, OD‑4).

### Q8 — How do assets interact with format specialization?

Format Specializations may state **requirement categories and counts** at Stage Attachment Point ASSET PREPARATION (STG‑06) — e.g. "requires one primary logo placement," "requires one footer-platform placement" — but never assert asset identity, specification, or visual-reference content. Those remain owned, respectively, by CAR ("CAR owns identity and registration, not asset specifications or visual-reference detail" `[CAR v1.10, Authority boundary]`), CAB ("CAB owns asset specifications. CAR owns identity; CRS owns visual-reference documentation" `[CAB v1.11, Authority boundary]`), and CRS (the detailed visual-reference specification; CRS's own field is named "Source-of-truth boundary," not "Authority boundary" `[CRS v1.5 §1, field "Source-of-truth boundary"]` — noted precisely here per the Evidence Citation Standard's own citation-integrity rule against inventing a field name a source does not use `[Evidence Citation Standard §12]`). `[REV1.0 §6 STG‑06]`'s own Output Contract — every requirement satisfied by a CAR-identified asset at CAS Canonical Lifecycle state `CANONICAL` or `CANONICAL LOCKED` — is unchanged by any format; a format cannot loosen it, and does not need to tighten it, since the constraint is already absolute.

A category may, for illustration, point at the class of asset a currently-registered CAR object satisfies (e.g. "primary brand-logo placement, currently satisfied by `CWC-OBJ-000001`"). Doing so states the requirement **category** only — it does not fix, and must not be read as fixing, which specific CAR-identified, CAS-canonical asset instance ultimately satisfies it. That resolution happens at STG‑06 under CAR/CAB/CRS's own authority (§15), never inside the Format Specialization Object itself; a naked CAR Object ID appearing in a format record is a pointer to a category, not a claim of asset identity by the format.

### Q9 — How does a new format get added?

Through the Format Addition Gate, §13.

### Q10 — How does a format evolve?

Through the three-axis versioning model, §14.

## 9. Inheritance / Extension / Constraint Rules

Three declarable rule modes, exhaustive by construction for what a format may *state* (every instruction a format could give reduces to: accept unchanged, add without changing, or narrow without contradicting) — plus one non-declarable validation classification that exists only to catch a fourth possibility (attempt to replace):

| Mode | Meaning | How it is expressed |
| -- | -- | -- |
| **INHERIT** | The format accepts a Core Workflow requirement unchanged. | Never declared explicitly. Represented **solely by omission** — a Stage not listed in `stage_attachments` (§8) is INHERIT for every one of its clauses. A `stage_attachments` entry, once present for a Stage, must declare `rule: EXTEND` or `rule: CONSTRAIN` and at least one concrete clause (§12, Completeness) — an explicit, populated `rule: INHERIT` block is not a valid serialization and is rejected by Structural Validation (§12). |
| **EXTEND** | The format adds a new requirement in a class the Core Workflow left open (Q4), without touching any existing Core Workflow clause. | Declared as `rule: EXTEND` at any Stage Attachment Point listed as EXTEND-eligible in §10. |
| **CONSTRAIN** | The format narrows an existing generic Core Workflow clause (typically an Exit Criterion or Output Contract clause) into a stricter, still-satisfiable form. A CONSTRAIN clause must be provably a *subset* of what the Core clause already permits — it can never require something the Core clause would reject, and it can never relax anything the Core clause requires. | Declared as `rule: CONSTRAIN`, only where §10 marks the Stage Attachment Point CONSTRAIN-eligible. |
| **FORBIDDEN OVERRIDE** *(not a declarable mode)* | Any attempt to replace, weaken, skip, or redefine a Core Stage, Lifecycle State, Exception Status, Quality Gate, transition rule, Revision Event mechanism, Governance mechanism, Approval checkpoint, or Publication/Cancellation boundary. | Never written into a Format Specialization Object by an author — structurally, `rule` may only hold `EXTEND` or `CONSTRAIN` (§8); `INHERIT` and `FORBIDDEN_OVERRIDE` are not legal enum values at all. This label instead names the **classification Workflow Conformance validation (§12) assigns** to a declared `EXTEND`/`CONSTRAIN` clause that, on inspection, actually does one of the things in the left column. |

This model is what prevents a Format Specification from "silently becoming a fork": every clause in every Stage Attachment Block carries one of the two legal declared modes (or is absent, i.e. inherited), and Workflow Conformance validation (§12) reclassifies as FORBIDDEN OVERRIDE — and rejects — any clause that is, on inspection, actually a prohibited change mislabeled as EXTEND or CONSTRAIN — e.g. an "EXTEND" clause that adds a new terminal state, or a "CONSTRAIN" clause that is looser, not stricter, than the Core clause it claims to narrow.

| VISUAL PRODUCTION | EXTEND, CONSTRAIN | `[REV1.0 §6 STG‑07]` Required Inputs already names "Format Specialization visual requirements" explicitly; Output Validation already reads "Self-check against Format Specialization visual requirements and the Reserved-Area rule." |

| RECORD | INHERIT only | Terminal; not a Stage Attachment Point. |

Per §9, an entry of "INHERIT only" in the table above means: **no** `stage_attachments` **entry should be authored for that Stage at all.** INHERIT is never itself a declared `rule` value in the schema (§8) — it is simply the state of a Stage not appearing in `stage_attachments`.

## 12. Validation and Conformance

Six checks, each testing a distinct failure mode, run against a Format Specialization Object before it may be registered (§13) or after any subsequent amendment (§14):

| Check | Tests | Failure disposition |
| -- | -- | -- |
| **Structural Validation** | Object conforms to the §8 schema — required fields (`format_id`, `format_name`, `status`, `version`) present, with `status` restricted to `DRAFT`/`REGISTERED` (§8, §18 OD‑1); `stage_attachments` (if any) use only recognized Stage names and only `rule: EXTEND` or `rule: CONSTRAIN` — a `stage_attachments` entry carrying `rule: INHERIT`, or any value other than `EXTEND`/`CONSTRAIN`, fails Structural Validation outright (§9). | Rejected before review; not a Format Definition until structurally valid. |
| **Workflow Conformance** | No Stage Attachment Block declares or effects a FORBIDDEN OVERRIDE (§9) — checked both by declared rule value and, independently, by inspecting whether an EXTEND/CONSTRAIN clause is *actually* one (e.g. a "CONSTRAIN" clause that is looser than the Core clause it claims to narrow is a conformance failure, not a valid CONSTRAIN). | Rejected; returned for correction. This is the check that directly answers Test F (§19) — "No" a format may never accidentally override a Core Workflow rule, because this check exists specifically to catch it. |
| **Dependency Conformance** | Every Asset-Requirement category is stated as a category/count and, where an existing CAR/CAB/CRS-owned identifier is named for illustration, that identifier points at the category rather than being asserted as the format's own requirement (§6 Q8); every Validation-Requirement contribution is additive to, not a replacement of, `[REV1.0 §6 STG‑08]`'s existing QA mechanism. | Rejected; the offending clause must be rewritten as a request *to* CAS/CAR/CAB/CRS (out of this document's authority to grant) rather than an assertion *by* the format. |
| **Conflict Detection** | Cross-checks every populated Stage Attachment Block against the corresponding Core Stage Contract `[REV1.0 §6]` for direct contradiction (an EXTEND clause that duplicates or contradicts an existing Required Input; a CONSTRAIN clause that is unsatisfiable given the Core Output Contract). | Rejected; contradiction must be resolved before registration — an unresolved contradiction discovered *after* registration, against a live Content Item, is a Canonical/Policy Ambiguity per `[REV1.0 §14.2]`'s deterministic test, routed to `GOVERNANCE_REVIEW`, not silently reconciled. |
| **Completeness** | Every populated Stage Attachment Block states a rule value and at least one concrete clause (no empty or placeholder blocks); `dependencies` cites real, checked sources, not asserted ones. | Rejected; incomplete records are not promoted to `REGISTERED` (§8, §11) — they may remain `DRAFT` while incomplete. |
| **Executability** | Every format-specific requirement is concrete enough for deterministic downstream execution, per the same conditional-determinism standard `[REV1.0]` already applies to itself: "Deterministic execution is supported where the referenced contracts, specifications, and explicit human decisions provide the required inputs; where a required decision or contract is unresolved, the workflow routes to the appropriate exception or human checkpoint rather than allowing agent inference" `[REV1.0 §4, principle 12]`. This document does not claim a stronger determinism guarantee than `[REV1.0]` itself claims. | An underspecified requirement is marked `[UNCONFIRMED — SOURCE GAP]` or `[OWNER DECISION REQUIRED]` directly inline within the specific clause that is underspecified — every clause field in §8 (`additional_inputs`, `additional_core_activities`, `additional_output_elements`, `additional_output_contract_clauses`, `production_requirements`, `additional_asset_requirement_categories`, `additional_validation_criteria`, `additional_handoff_detail`) is free text and can carry the tag directly — and, where the gap is structural rather than confined to one clause, recorded in that object's own `change_log` entry (`change`/`basis` fields, §8). The schema defines no separate `notes` field, and none is added for this purpose (§8 stays minimum-viable). The corresponding Content-Item-level execution routes to `GOVERNANCE_REVIEW` if actually encountered unresolved — never to silent agent inference. |

```text

      v

      |
      v

      |
      v
Workflow Conformance  (§12)  ---- fail ----> returned for correction
      |  pass
      v

      |  pass
      v
Human Approval  (Owner — same authority pattern already used to canonicalize
      |          CPB/CAS/CAR/CAB/CRS/REV1.0; see §15 and §18 OD-2)
      v
Registered Format  (status -> `REGISTERED` in the Format Registry, §11 — a
                     registration fact FSS-001 itself defines and owns; not a
                     claim that any broader Content OS canonical-lifecycle
                     vocabulary now applies to this object, which remains
                     OD-1, §18)
```

**Important distinction, deliberately drawn to prevent a subtle authority conflict:** the "Human Approval" step above is **document-level registration** of a Format Specialization Object — an Owner decision about a production-layer artifact — and is categorically distinct from **STG‑09 Approval** in `[REV1.0]`, which is a per-Content-Item publication-authority decision `[REV1.0 §6 STG‑09, §18]`. Registering `FORMAT-POSTER` as `REGISTERED` does not grant, imply, or shortcut STG‑09 Approval for any individual Content Item produced under it. Conflating the two would itself be a FORBIDDEN OVERRIDE of the Approval checkpoint (§10, APPROVAL row) and is explicitly rejected here. No new governance gate is introduced beyond what `[REV1.0]`'s own Owner-approval pattern (already evidenced for CAS: "Promotion between states…is an Owner decision…not automatic" `[CAS v1.11 §6]`) already provides — the Format Addition Gate reuses that authority model, it does not invent a second one.

## 14. Versioning and Change Control

This section states FSS-001's own architectural design decision for how it manages change across three layers — consistent with, but not derived from, Root Governance's general per-document versioning rule ("Version increments on every architectural change," `[Root Governance v1.11 §6, step 6]`, which does not itself mandate multiple independent axes within one document's own object model). The three-axis separation below is this document's own choice, made to prevent exactly the kind of version conflation the governing task warned against.

Three independent version axes, never conflated:

```text
Core Workflow version        (REV1.0, currently locked; future amendments follow
    ≠                          REV1.0's own Amendment discipline and Canonicalization
                                Record, §0.3/§0.4/Canonicalization Record of REV1.0)
FSS specification version     (CWC-FSS-001, this document's own vX.Y)
    ≠
Individual format version     (e.g. FORMAT-POSTER vX.Y, independently incremented)
```

* **A Format version change** (e.g. `FORMAT-POSTER` v1.0 → v1.1, adjusting a slide-count constraint) never touches this document or `[REV1.0]`. It re-runs Validation (§12) against the amended Format Specialization Object only. A Content Item already mid-lifecycle under the prior Format version is not silently migrated to the new version — per the ContentOS Project's own stated working-basis discipline (`[ContentOS Project description]`: "silent substitution antarversi dilarang; ambiguity harus dieskalasikan"), an in-flight Content Item either completes under the version it was assigned at Planning, or a version change to it is an explicit Revision Event `[REV1.0 §11]`, never an implicit reassignment.
* **An FSS-001 specification revision** (e.g. adding a new addition class to Q4, or a new rule-system value) never touches `[REV1.0]`. It does, however, require re-validating every already-registered Format Specialization Object against the revised schema — the same "stale Depends On" re-synchronization pattern this workspace already practices for CPB/CAS/CAR/CAB/CRS whenever Root Level Architecture or Root Documentation Structure changes upstream. This is an empirical pattern observed directly in each of those documents' own retrieved amendment histories (e.g. `[CPB v2.10, CAS v1.11, CAR v1.10, CAB v1.11, CRS v1.5 — each Document Identity, Status field, "synced Depends On" entries]`), not a rule stated in general terms by any single canonical source; this document's adoption of the same pattern for itself is `[ARCHITECTURAL INFERENCE]`, not a cited requirement.
* **A Core Workflow amendment** that changes Stage/State/Exception/Transition/Revision/Governance semantics is, by `[REV1.0]`'s own Amendment discipline, a substantive change producing a new Workflow version. Such a change potentially invalidates this document's Stage Attachment Model (§10) and every registered Format's Workflow Conformance status (§12), and **must be flagged for explicit FSS-001 re-validation — never silently propagated**, consistent with the same silent-substitution prohibition cited above and with `[REV1.0]`'s own "No silent exit" / "Evidence before assumption" principles `[REV1.0 §4]`.

A change that only corrects wording, a citation, or a P2-class precision issue in a Format Specialization Object (analogous to `[REV1.0]`'s own `BUS-40` non-blocking citation-precision follow-up) is a compliance amendment, not a version-triggering substantive change, exactly on the pattern `[REV1.0]`'s own Canonicalization Record already establishes for itself: *"A change that only resolves one of the open items above, or applies the P2 corrections, is a compliance/content amendment (no change to canonical substance) unless it alters lifecycle, transition, revision, exception, or governance logic — in which case it is a substantive amendment"* `[REV1.0, Canonicalization Record, "Amendment discipline going forward"]`.

## 17. Invariants

* **INV‑FSS‑1** — A Format Specialization never introduces a Stage outside `[REV1.0 §5]`'s eleven-stage sequence.
* **INV‑FSS‑2** — A Format Specialization never redefines a Lifecycle State or Exception Status value (restates `[REV1.0 §20]` INV‑FMT‑1 at this document's own layer).
* **INV‑FSS‑3** — A Format Specialization never bypasses Gate‑QA, Gate‑Approval, or Gate‑Publication `[REV1.0 §12.1]`.
* **INV‑FSS‑4** — Format-specific validation requirements are consumed only as part of STG‑08's existing "applicable QA criteria" input; QA's Output Contract (verdict recorded + FAIL classified) is never altered per format.
* **INV‑FSS‑5** — Format-specific Asset Requirements state categories/counts only; they never assert asset identity, specification, or visual-reference content owned by CAR/CAB/CRS.
* **INV‑FSS‑6** — The Content Item remains the sole workflow unit; Format is carried as its attribute, assigned **exactly once** at STG‑04 (§3, §5) — a Content Item never carries more than one assigned Format Specialization concurrently, and no agent may infer or compose a concurrent multi-format assignment at runtime; Format is never a competing workflow unit.
* **INV‑FSS‑7** — A CONSTRAIN-class clause must be a provable subset of the Core clause it narrows; it is a conformance defect (§12) if it is not.
* **INV‑FSS‑8** — Format Specification versioning (§14) is independent of Core Workflow versioning and of any individual Content Item's lifecycle; a Format version change never implicitly migrates an in-flight Content Item.
* **INV‑FSS‑9** — No Format Specialization Object may populate a Stage Attachment Block at APPROVAL, PUBLICATION, or RECORD beyond INHERIT (§10).

## 18. Open Decisions

* **OD‑1** `[OWNER DECISION REQUIRED]` — Should a broader canonical-lifecycle vocabulary (e.g. CAS's `DRAFT → REVISION CANDIDATE → CANONICAL → CANONICAL LOCKED`, `SUPERSEDED` progression, `[CAS v1.11 §6]`; or Root Governance's root-level `Draft`/`CANONICAL` pair, `[Root Governance v1.11 §4.1]`, itself explicitly scoped to root-level documents' Status field and not stated to extend to Tier 2 Format Objects) eventually govern a Format Specialization Object's own lifecycle, beyond registration? As established since v1.2 and retained in v1.4, the schema (§8) no longer presupposes an answer: `status` is restricted to `DRAFT`/`REGISTERED`, a minimal registration-state vocabulary FSS-001 defines and owns for itself (§11, §13), deliberately decoupled from any broader canonical-lifecycle claim. This is a narrowing of OD‑1's *immediate operational surface*, not a resolution of the underlying question — whether Format Specialization Objects should ever progress through a fuller lifecycle (and if so, which one) remains genuinely open and is not decided here.
* **OD‑2** `[OWNER DECISION REQUIRED]` — Is the Format Addition Gate's "Human Approval" step (§13) necessarily the same Owner identified throughout `[REV1.0 §18]` and CPB/CAS/CAR/CAB/CRS, or may it be delegated to a different, still-human, review role? No retrieved source defines a delegation model for canonicalization/registration authority.
* **OD‑3** `[OWNER DECISION REQUIRED]` — **Future architectural-capability question, not a current execution ambiguity.** The current model is explicit (§3, §5, §6 Q1, INV‑FSS‑6): a Content Item carries exactly one assigned Format Specialization at STG‑04, on the `[ARCHITECTURAL INFERENCE]` drawn from `[REV1.0 §6 STG‑04]`'s singular "assigned Format Specialization" wording — this is not stated by `[REV1.0]` as an explicit platform-wide cardinality rule. Concurrent assignment of multiple Format Specializations to one Content Item is **not supported by the current model**, and no agent may infer or compose a concurrent multi-format assignment implicitly at runtime. OD‑3 asks a separate, forward-looking question: should a future capability for concurrent multi-format assignment (e.g. content repurposed from Reel into Story) ever be introduced? Doing so would require an explicit architectural amendment to this document — a deliberate schema/cardinality redesign, not an inference from today's wording — and is neither decided nor foreclosed here. This is a future capability decision, not a defect in the current architecture.
* **OD‑4** `[OWNER DECISION REQUIRED]`**, inherited unresolved from the Core Workflow** — QA checklist ownership `[REV1.0 §21 Appendix B, item B‑5 / BUS-38]` remains open at the Core Workflow level. §6/Q7's architecture (format-specific criteria feed the single existing "applicable QA criteria" input) is sound regardless of how B‑5 resolves, but this document cannot fully close its own Executability check (§12) for any given format's validation clauses until B‑5 is resolved.
* **OD‑5** `[ARCHITECTURAL INFERENCE]` — Should individual format-specific clauses (e.g. a Poster headline-length constraint) themselves carry Evidence Citation Standard citations back to CPB when they are substantively derived from it? Recommended for consistency with this document's own discipline, but not settled by any retrieved source specifically for Format Definitions — left to the format-authoring process, not mandated here as a schema requirement (§8 does not add a citation field, to avoid overspecifying a layer this document explicitly declines to design).

No item above alters `[REV1.0]`'s existing five Open Decisions (`BUS-35`–`BUS-39`); none of B‑1, B‑2, B‑4, B‑6 is implicated by this document's architecture, and B‑5 is referenced (OD‑4) but not reopened or resolved. None of OD‑1 through OD‑5 is closed by this document as of v1.4 — OD‑1's *operational surface* was narrowed in v1.2 and remains narrowed, unchanged, in v1.4 (see above), which is progress on containing its blast radius, not a resolution of the question itself.
